# PDR-0017: Identifier formats: vendor.product and LIC-XXXXX-XXXXX

- **Status:** Decided, 2026-09-30. Amended, 2026-10-02: adds the key identifier
  `LIC-XXXXX-XXXXX-XXXX` (PDR-0020). Amended, 2026-10-03: adds the vendor tag format (PDR-0022)
- **Source:** raised while writing the schema in [`docs/license-examples.md`](../license-examples.md);
  amendments: `openspec/changes/license-key-management/design.md` Q5, Q21
- **Serves:** site owner (sees whose key it is; reference easy to read and type), implementor (readable routing key), vendor (uniqueness within its own records)

## Decision

**Product ID:** `vendor.product`. Two dot-separated parts of lowercase `a-z`, digits and
hyphens, each starting with a letter, e.g. `acme.commerce`. Issuing rejects anything else.
Guidance: choose a vendor part the vendor already owns uniquely, such as its domain or its
package-registry owner name.

**License reference:**

| Aspect | Rule |
|---|---|
| Characters | Uppercase letters and digits, excluding look-alikes `0 O 1 I L` |
| Length | 10 random characters, shown in two groups of 5 |
| Display | `LIC-7K3QM-X9P2D`; the `LIC-` prefix is display only |
| Matching | Ignores case, hyphens and spaces |
| Generated by | The core, at first issue. On reissue the caller passes the existing reference in |

**Key identifier** (added 2026-10-02; what it is for: PDR-0020):

| Aspect | Rule |
|---|---|
| Form | The license reference followed by a key part: `LIC-7K3QM-X9P2D-4TQ9` |
| Key part | 4 random characters from the reference's alphabet |
| Generated by | The core, at every issue including a reissue. Never a caller input |
| In the key string | The key string starts with the identifier written as displayed, so the text a result shows can be searched for as it stands |
| Matching | Ignores case, hyphens and spaces, as for the reference |
| Unique | Within one reference |

**Vendor tag** (added 2026-10-03; what it is for: PDR-0022):

| Aspect | Rule |
|---|---|
| Characters | `A-Z a-z 0-9` and `- _ . # /`; no spaces |
| Length | 1 to 64 characters |
| Case | Kept as supplied; the library never compares it |
| Generated by | Never. Optional vendor input; an invalid value is rejected, never cleaned |
| Unique | Not required, not checked |

## Why

- **Product ID.** The store is shared by all vendors (PDR-0002), and the inventory,
  registration (PDR-0004) and routing all key on the product ID. The signature stops one
  vendor's key unlocking another's product, but not a confusing collision in the inventory. The
  ID is permanent, carried by every issued key. A vendor prefix makes a collision require two
  vendors choosing the same prefix, and keeps the ID readable where it matters most: a key with
  no registered product is shown by product ID alone (PDR-0003).
- **Reference.** It is read aloud on support calls, typed into order forms and passed in
  renewal links (PDR-0009). The core keeps no records (PDR-0005), so it cannot check a new
  reference is unused; uniqueness comes from randomness. Harm from a collision:

  ```
  different sites        -> harmless; references supersede only within one site
  same site, same product -> one silently supersedes the other (vanishingly rare)
  vendor's records        -> "renew LIC-X" finds two; the add-on (PDR-0006) or the
                             vendor's systems check and regenerate
  ```

  10 characters from 31 gives about 800 trillion combinations: a vendor issuing 100,000
  licenses per product has roughly a 1 in 150,000 chance of any clash in its records.
- **Key part.** It only has to tell apart the keys issued under one reference, so it is short.
  4 characters from 31 gives about 920,000 combinations: a license reissued 36 times (a
  monthly add-on over three years) has roughly a 1 in 1,500 chance of any clash. With 2
  characters the same license would have about an even chance. Harm from a clash: two key
  strings under one reference share an identifier, so a result row could mean either. Their
  states still differ (one superseded, one not), and nothing is granted or lost.

## Rejected

| Option | Why rejected |
|---|---|
| Product ID as free text | Two vendors can pick the same ID |
| Product ID as the package's published ID | Ties a license to one package name, which can be renamed or split; a product ID can never change |
| Product ID as a random identifier | Unique but unreadable, e.g. `7f3a9c...` in an inventory row the site owner cannot identify |
| Reference uniqueness enforced by the core | The core keeps no records |
| A key part of 2 characters | Clashes are likely on a license reissued often (see Why) |
